# TesorerIA contracts

`Fund` holds a group's shared money in wARS (and USDT until the agent converts it) on Celo. The agent can only:
- convert USDT to wARS within 2% of the pool's 30-minute TWAP;
- reimburse the expense the group agreed on, to a member, up to a weekly cap.

Everything else (other payments, member changes, the weekly cap, quorum, replacing or firing the agent, closing the fund) needs N-of-M member votes, with N always below M so one lost passkey can't lock the fund; the total cap is fixed when the fund is created. The agent can propose these actions but never votes. Once the fund is closed, anyone can call `distributeRemainder` to split, by the same rule, whatever reaches it later. `FundFactory` deploys one `Fund` per group.

## Run the tests

    git clone https://github.com/ruizemanuel/TesorerIA && cd TesorerIA/contracts && git submodule update --init   # no --recursive needed
    forge build
    FOUNDRY_PROFILE=ci forge test                 # unit, fuzz and invariant tests with mocks, no network
    forge test --match-path "test/fork/*" -vv     # against a local fork of Celo mainnet

## Security review

Internal review before the first mainnet deploy, not an external audit: Slither 0.11.6 and the Pashov checklist over `src/`. It was first done on 2026-10-08 and redone after the pre-deploy changes: N below the member count, `distributeRemainder`, and a swap callback that pays at most the converted amount, once. No finding needed a code change. Line numbers are in `src/Fund.sol` unless noted.

### Slither

`slither . --filter-paths "lib/|test/" --exclude-informational` reports 13 results: 2 High, 8 Medium and 3 Low, all justified below.

- **High, `reentrancy-balance` in `convert` (2 results, one per swap direction; `:246`, `:248-254`, `:257`).** False positive. Reading the wARS balance before and after `pool.swap` is how the fund measures what actually arrived. Nothing can take wARS out of the fund during the swap: `convert` holds the `nonReentrant` lock, as does every other function that moves tokens except the swap callback, and the callback pays USDT only to the pool, only while `convert` runs, at most `usdtAmount` and only once (`:263-269`). An outside transfer during the swap could only add wARS. The pool address is immutable. The real wARS and USDT have no transfer hooks today, but both are upgradeable (see Centralization).
- **Medium, `incorrect-equality` (5 results).** False positive. `total == 0` in `_split` (`:465-466`) and `totalContributed == 0` in `_shareOf` (`:421`) compare internal accounting that a token transfer cannot change, and guard a division by zero. `usdtAmount == 0` in `quoteUsdtInWars` (`:185`) is an early return; a USDT donation only turns a zero into the correct quote of the donated amount. `bw == 0 && bu == 0` in `distributeRemainder` (`:451`) only rejects a call with nothing to split; a donation just gives the call something to split.
- **Medium, `unused-return` (3 results).** Intended. `_averageTick` (`:198`) only needs the tick cumulatives from `pool.observe`. `convert` ignores the amounts returned by `pool.swap` (`:248-254`, 2 results): the wARS received is measured by balance difference and checked against `minWarsOut` (`:256-257`), and the callback checks the USDT side itself: it pays only the USDT delta, only if it is positive and at most `usdtAmount` (`:266-267`).
- **Low (3 results).** `reentrancy-benign`: `_swapUsdtLimit = 0` is written after the swap (`:255`) on purpose, since the limit has to cover it; it lives in transient storage, so it can't outlive the transaction either. `timestamp`: proposal expiry (`:361`) uses `block.timestamp` on purpose (proposals last 7 days, so seconds of drift don't matter); the flagged `id >= _proposals.length` checks (`:347`, `:358`) don't involve time.

The 20 forge-lint warnings in `src/` were also reviewed and left as they are. Every `unsafe-typecast` is bounded: `uint128` is checked at `:186`, the TWAP tick fits `int24`, `int256(usdtAmount)` is capped by the USDT balance, the callback casts the USDT delta only after checking that it is positive and at most `usdtAmount`, the `uint8` `votesRequired` is below 10, and the `uint64` is a timestamp. The modifiers before `nonReentrant` only read storage. The `reentrancy-events` sit in `nonReentrant` functions or, in `FundFactory.sol:33`, after a constructor that only makes view calls. The rest repeat Slither's `unused-return` and `timestamp`, plus a revert inside the constructor's validation loop.

### Pashov checklist

1. **Reentrancy: PASS.** Every function that moves tokens is `nonReentrant` (OpenZeppelin `ReentrancyGuardTransient`): `contributeWars`, `contributeUsdt`, `convert`, `reimburseAgreedExpense`, `execute` and `distributeRemainder` (`:205`, `:210`, `:237`, `:279`, `:326`, `:448`), except the swap callback, which only runs inside `convert`: instead of the lock, it requires `msg.sender == pool` and a pending limit that `convert` sets and the first payment clears (`:264-268`). Tests have a third party call it in the middle of a conversion, and the pool ask for more than `usdtAmount` or collect twice. State changes come before transfers in reimbursements (`:286`), execution (`:329`), member removal (`:380-383`) and closing (`:440`). Contributions pull the tokens before crediting, to credit what actually arrived; the lock covers them.
2. **Overflow: PASS.** Solidity 0.8.37 checked arithmetic. `src/` has no `unchecked` blocks; the only ones on its paths are in Uniswap's `TickMath.getSqrtRatioAtTick` and `FullMath.mulDiv`, reached through `OracleLibrary.getQuoteAtTick`. Narrowing casts are bounded (see forge-lint above).
3. **Access control: PASS.** `onlyMember` (`:130`) guards contributions and votes, `onlyAgent` (`:135`) guards conversion and reimbursement, `propose` takes members or the agent (`:303`), and `whenOpen` (`:140`) guards every state change except the swap callback, which only runs inside `convert`, and `distributeRemainder`, which only runs once the fund is closed (`:449`). Anyone can call `execute`, but it needs N votes (`:328`); anyone can call `distributeRemainder`, but it only splits by the close's rule. The constructor checks 3 to 10 distinct non-zero members, an agent who is not one of them, 2 ≤ N < members, a non-zero total cap and the pool's tokens (`:147-160`). The factory has no privileged functions.
4. **Front-running and MEV: PASS.** `convert` rejects a `minWarsOut` below 98% of the 30-minute TWAP quote (`:243`) and reverts if less than `minWarsOut` arrives (`:257`). The swap has no price limit (`:252`), so a sandwich can take at most the gap between the market price and `minWarsOut`; the agent should set `minWarsOut` near the current quote, not at the floor. USDT contributions are credited at the TWAP, not the spot price. Reimbursements, payments and the closing split don't depend on prices.
5. **Oracle manipulation: PASS.** The only price is the pool's 30-minute TWAP from `observe` (`:195-202`), rounded toward negative infinity like Uniswap's `OracleLibrary.consult`. It sets USDT credits, the total cap check and the conversion floor. A price moved within one block barely moves it, but the pool is thin, so holding a moved price for longer may be cheap. What bounds the damage is the fund's total cap (`balanceCap`, fixed at creation: the app will propose 450,000 wARS, about US$300, but the contract accepts any non-zero cap), the vote needed to take any gain out of the fund (`RemoveMember` or `Close`), and the agent's own comparison with Chainlink before converting, which lives off-chain, in the agent. The oracle can also be blocked for a while: the real pool keeps 1,200 observations, at most one per block, so touching it in every ~1 s block leaves only about 20 minutes of history, and then `observe` reverts (`OLD`), as it does for a pool with less than 30 minutes of history. Meanwhile `contributeUsdt`, `convert` and `contributeWars` (when the fund holds USDT, through `balanceInWars`) revert too, but votes, payments, reimbursements and the exits (`RemoveMember`, `Close`, `distributeRemainder`) don't use the oracle: a denial of service, not a loss. Anyone can enlarge the pool's buffer with `increaseObservationCardinalityNext`.
6. **Unchecked external calls: PASS.** Every token movement uses `SafeERC20`: `safeTransferFrom` (`:219`) and `safeTransfer` (`:269`, `:293`, `:384-385`, `:467-468`). Incoming amounts are measured by balance difference (`:218-220`, `:246`, `:256`); a test token that burns 1% of every transfer is credited only what arrived. The ignored returns of `pool.swap` and `pool.observe` are covered under Slither.
7. **Centralization: PASS.** `Fund` and `FundFactory` have no owner, admin, pause or upgrade path. The tokens do: wARS and Celo's USDT are upgradeable EIP-1967 proxies, so their issuers can change them, for example to charge transfer fees, add transfer hooks, pause transfers or blocklist addresses (see 9). Contributions credit only what arrives (`:218-220`), but a payout could deliver less than the fund sends. The agent can only `convert` (the wARS stay in the fund), `reimburseAgreedExpense` (to a member, within `weeklyCap` per week, `:281-286`) and `propose`. It never votes: only a member's proposal carries the proposer's vote (`:318`), and `vote` is `onlyMember` (`:321`). It can never be a member (`:157`, `:372`, `:388`, `:411`), and members replace or fire it with a `SetAgent` vote. A stolen agent key can cost at most `weeklyCap` a week, paid to members, plus up to 2% per conversion. N always stays below the number of members (`:153`, `:379`, `:407`), so one lost passkey can't block the vote that replaces that member; a group of 3 (N = 2) can replace a member but not remove one.
8. **Events: PASS.** Every state change emits an event: `Contribution`, `Conversion`, `Reimbursement`, `ProposalCreated`, `VoteCast` and `ProposalExecuted`; each executed action adds its own (`Payment`, `MemberAdded`, `MemberRemoved`, `MemberReplaced`, `WeeklyCapChanged`, `VotesRequiredChanged`, `AgentChanged`, `FundClosed`); `distributeRemainder` emits `RemainderDistributed`; and the factory emits `FundCreated`. `FundClosed(warsBalance, usdtBalance)` and `RemainderDistributed(warsBalance, usdtBalance)` emit the balances read before the split, including the rounding dust that stays behind. Tests pin the exact data of `Contribution`, `Conversion`, `Reimbursement`, `ProposalCreated`, `VoteCast`, `Payment`, `ProposalExecuted` and `RemainderDistributed`.
9. **Tokens with a blocklist: FAIL (known risk, governance workaround).** wARS has a `COMPLIANCE_ROLE` (off today) and Celo's USDT has a blocklist (`isBlocked`). Payouts are pushed, so if a member who is owed a share gets blocklisted, closing (`:467-468`) and removing that member (`:384-385`) revert for everyone, as do payments to them. Workaround: vote `ReplaceMember` to another address of the same member (it moves no tokens), then close. After closing, members can't be replaced any more, so a member blocklisted later blocks `distributeRemainder` for both tokens whenever they are owed a share of the blocked token, until the blocklist is lifted. If the fund itself were blocklisted, its balance of that token would be frozen and the contract can't prevent it.
